# Library Lab 剩余库质量整改设计

版本：v1，2026-11-10。入口：[路线图](roadmap.md)；执行记录：[任务日志](task-log.md)；新会话：[启动说明](start-here.md)。

## 需求与目标态

### 痛点

现有部分讲解先介绍内部维护细节，核心模型、选型条件和操作结果不清楚；部分 Demo 通过更换数据或输出格式凑层次。抽查证据见[质量审查](../../../docs/library-lab/quality-audit.md)，它是抽样记录，不能推断每个库都有相同问题。

当前目录有 119 个库。C20、D15、F18 已完成本轮样板整改，剩余 116 个需要逐库核实、修改和复核。A06 已有审批工作台改动，保留其成果后补齐质量要求。三份样板和公共接线仍是未提交的工作区成果，依据见[本地验证](../../../docs/library-lab/evidence/quality-c20-d15-f18-local-validation.md)。

### 目标态判据

读者是有经验、首次接触目标库的 React 工程师。每个库都能让读者回答：解决什么问题、何时选它、关键机制是什么、如何接入、操作后看见什么结果，以及迁入项目要保留哪些前提。

116 个库都有逐库记录，讲解、真实示例、Agent 指南和官方资料相互对应；已有高质量部分经复核后复用。最终统计分别展示内容整改、真实运行、正式收据和阻塞数量。

### 验收门槛

| 项目 | 可核对的门槛 |
| --- | --- |
| 内容质量 | 按 `library-lab-quality/references/review-and-validation.md` 的六项逐项给状态和证据；适用项有缺口时不能记 content_done |
| Demo | 每库 1–3 个独立学习目标；正文、操作、源码和真实结果对应；不以截图或手写输出代替 SDK |
| 官方资料 | 官方中文优先、原文快照固定提交且摘要正确；官网按依据记 allowed/blocked/unknown，保留直达入口 |
| 覆盖 | queue.json 与当前目录对账：116 个唯一待整改身份；3 个样板单列；新增/删除身份须显式调整计划 |
| 可恢复 | 每次所有权、状态或证据变化都落盘；任何新会话可从 start-here.md 找到下一项 |

### 不在本次范围内

- 发布、推送、合并与 Git 提交：当前授权是整理计划及随后修改库；用户另行授权交付 Git 时再执行。
- 模板、create-reactloom 与公共部署：Lab 保持私有；只有目标明确变更时才重新界定范围。
- 批量升级依赖与强制三个 Demo：先满足当前锁定版本的教学目标；确有版本兼容问题再提出公共依赖请求。
- 常驻自动化服务：自动调度由用户开启的新会话执行；跨会话靠文件恢复，不假设模型会自行启动下一会话。

## 3. 决策

### 决策 1：以单个库的完整学习闭环作为交付单位

讲解、1–3 个真实 Demo、可迁移源码、官方 README、官网展示和六项复核共同交付。每阶段对应一个库，覆盖116个；共享的调度批次只负责资源编排，不把多库拼成一个验收对象。按[change 拆分标准](../../../../../../.sdflow/workflow/reference/change-decomposition-standard.md)理解内聚边界，未来实施按当前可用工作流承载。

替代方案是先改完所有文案再补全部 Demo。它会形成大量半成品，无法从一库判断体验是否改善。单库交付更易阅读验收和恢复，代价是重复的资料核实；公共接线和验证结果在有效范围内复用。

### 决策 2：风险优先，先细化两库，再滚动细化

先处理 E05 Monaco 的讲解/宿主偏差和 E11 Streamdown 的薄弱讲解，随后是 F05、B09、A06 等已抽查风险；其余按库族顺序处理。具体顺序与身份在 queue.json，路线图提供人可读视图。后续目标是设计假设，不能冒充已确认缺陷；先读真实源码再决定改写深度。

替代方案是预写116份完整实施 spec，或者不留队列临时选库。前者会把未核实的事实写死，后者会漏库。接受远期没有精确 Demo 数与工期，进入候选前补齐库的五节实施说明；依据不变的细化由主控自主完成，范围、不可逆承诺或验收变化再按 roadmap review 规则复审。

### 决策 3：主控串行写共享文件，工作者只写独占目录

新会话按实际容量派发独立条目任务，容量未知时串行。已知总容量为 N 时，最多 N−1 个在途子代理；当前环境可用时建议最多3个条目工作者。每个工作者明确“并非独自在仓库中；保留他人修改”，只拥有本条目目录。跨条目引用只读。

主控拥有 queue.json、results/、task-log.md、公共 src/scripts/tests/e2e/runners、package/lockfile、根索引。工作者把新公共需求、依赖及 e2e 场景交给主控处理；需要共享改动时暂停受影响条目，先完成公共依赖再继续。禁止并行生成 public/raw、改锁或同时运行占同端口/相同产物目录的任务。结果复核可使用空闲槽位；不能靠创建新代理反复重做已通过的检查。

共享验证采用输入稳定屏障：运行读取全目录的 generate、typecheck、build，或会隐式 build 的 Playwright 前，主控收齐所有在途写入者的稳定检查点确认，暂停这些条目和公共输入的修改，记录本批候选文件摘要后执行验证，结束再释放写入。不能把“只有一个生成器”当作输入已稳定。单条 SDK 检查只冻结其实际输入；若需要并行验证，使用包含当前 dirty 成果的完整候选副本，并注明其输入绑定，不从 HEAD 丢弃未提交工作。

替代方案是所有工作者均可修改公共文件，冲突和指纹失效会反复出现。单一主控增加少量集成工作，但减少冲突与重复全量构建；并行数服从当前宿主，不把本机容量当全局常量。

### 决策 4：状态与证据分离，保留正式记证边界

queue.json 的工作状态只允许 `pending → in_progress → review_pending → content_done`，任一步可进入 `blocked`；恢复时写明回到哪一步。`content_done` 需要六项适用条件通过，含实际运行证据；正式 sdk/build/browser 收据另行记录。工作者返回不等于完成，主控核对 diff、官方依据、实际结果和独立复核后才改状态。

每库结果写 `results/<ID>.md`：基线/改动文件、核心问题、Demo 目标、来源与版本、六项状态、命令/cwd/退出码/日志产物、复核意见处置、剩余项。queue.json 的 `result` 在文件存在后才能填相对路径，证据更新后再推进状态；task-log 倒序记录里程碑并回指阶段。主控采用临时文件加原子替换更新 JSON；派出任务前先保存认领，收到结果后先保存结果再改完成状态。

正式 PASS/FAIL 继续受 verify:record、干净已提交输入和收据指纹约束。无提交授权时继续完成可验证的内容工作，正式记证记为待提交后执行，不能为取得收据擅自提交或假写 PASS。缺浏览器、真实 SDK 或核心资源影响六项时，保留 blocked，不纳入 content_done。

### 决策 5：断点通过文件和当前差异恢复

queue.json 保存规划 HEAD、逐库非忽略文件的路径/字节摘要、共享依赖输入摘要及起始 dirty 文件列表；这是变更探测基线，**不是正式验收指纹**。摘要算法为对 Git 当前可见的 tracked 与 untracked 非忽略文件去重、按相对路径排序，对每个 `path + NUL + bytes + NUL` 累加 SHA-256。

新会话先核对当前 cwd、HEAD、diff 和文件存在性。遇到差异先识别已完成工作与活跃 owner，保留成果后追加基线变更说明，不能用规划快照反向覆盖。对 in_progress/review_pending 先查代理与结果；owner仍活跃就保持认领，owner已结束才审查残留 diff 并恢复。C20/D15/F18 仅在受影响输入变化时复核；A06 的现有审批工作台先读[本地证据](../../../docs/library-lab/evidence/a06-low-code-local-validation.md)，保留其设计/执行闭环。

替代方案是依靠会话记忆或先清空工作区，前者会丢状态，后者会丢成果。文件队列的代价是每次阶段变化要写检查点；不需要新的数据库或调度守护进程。

### 决策 6：按影响验证，阻塞只隔离依赖项

只改讲解：事实、源码对应、链接、格式与目录检查。改示例：实际目标库的定向检查，交互/存储/Worker 要在对应环境操作；Node/CLI 必须运行真实固定配方并解释产物。改公共运行、依赖或构建：扩展到相关平台测试、typecheck、build 和关键浏览器流程。生成及共享构建由主控在批次内统一安排；相同有效输入下复用证据，仅重跑失败或受影响检查。

缺资源、许可证、凭据或环境时写 `blockedAt / reason / unblockCondition / nextAction`，继续无依赖的库；相同阻塞未变不循环重试。E19 不自动设置许可证已审标志；B21/B22/C22 作为历史迁移条目；E11/F05 维持 reconstructed/summary-only 的真实来源属性。网页不给任意 shell 执行接口。官网无独立站用官方仓库，禁止嵌入按现有面板降级；unknown 必须有检查记录，不能冒称已允许。

历史迁移条目将源库的官方资料与替代库的实际运行分开标记；不能用替代库的README或执行结果冒充源库的原文与SDK验证。

## 4. 文件结构与更新所有权

```text

  design.md     # 目标、决策、边界
```

本计划不安装 OpenSpec 到项目、不生成116份 change 壳。若未来选择 sdflow-spec/ship/done，须读取其适用规则并将默认 commit/merge 行为限制在用户当时授权内；计划里的 change 名只是映射。

## 5. 风险与边界

| 风险 | 处理 |
| --- | --- |
| 未提交样板或 A06 被新会话覆盖 | 起始 dirty 清单 + 逐库摘要 + 先读 diff/本地证据；当前目录持续工作，不能从 HEAD 建新树后遗漏修改 |
| 资料漂移或中文仅在新版本 | 当次核对官方版本；记录差异，宁可原语言也不伪造官方中文 |
| 动态库需要 WebGL/Worker/大资产 | 分配匹配环境，记录真实限制；不以政策单测代替运行 |
| 生成器清空 raw 与活跃预览冲突 | 主控串行生成；记录开发缓存问题，验证候选用匹配构建的 preview；服务操作先查 owner |
| 正式全局指纹因公共修改失效 | 公共修改集中；最后在获准的干净提交上按受影响范围记证，不反复对所有库刷 PASS |
| 多会话状态写冲突 | 一份队列一个主控；发现另一活跃主控时协调所有权，再更新，不并发覆盖 JSON |
| 一次会话无法完成全部 | 留逐库检查点和下一项；只报告实际完成数，剩余可在下一会话恢复 |

遇到需回退的修改时只撤回本任务可归属的文件块，并先保留当前候选副本或 diff。禁止 reset/clean 覆盖并行成果。阻塞未解除且没有独立工作、资源耗尽或用户停止时，保存结果和下一步后准确汇报。

## 6. 尚待执行时核实的事项

每库当前官方 README 语言/ref、最终 Demo 数、真实 SDK/浏览器覆盖、外站嵌入结果和必要公共接线在进入该库时确定。规划阶段不批量宣称这些条件已经满足，不承诺未经测量的总工时。

## 附录：关键规划备选的取舍

| 决策与候选 | 系统影响 | 用户影响 | 开发循环影响 |
| --- | --- | --- | --- |
| 决策1：单库完整闭环（采用） | 修改与证据可按库定位、回退 | 较早获得可完整学习的条目 | 每库核实有重复，公共结果可复用 |
| 决策1：全库文案后再补Demo | 跨全目录半成品持续存在 | 长期只能看到部分改善 | 批量文案快，但最后集中发现源码不符 |
| 决策2：两库细化、远期队列（采用） | 远期随实际输入修正，变动局部 | 近期较快可见，远期时间不精确 | 减少过期spec；承担临近执行的调查成本 |
| 决策2：预写116份完整spec | 大量API/版本假设提前固化 | 全量计划更细，实际效果交付推迟 | 前置成本高，后续反复同步资料 |
| 决策2：无队列临时选库 | 缺少完整身份对账和恢复点 | 覆盖与先后不透明 | 起步轻，漏项和重复调查成本高 |
| 决策3：公共单主控、条目独占（采用） | 共享输入与产物可稳定绑定 | 各库整合后行为一致 | 主控有集成成本，减少冲突与重复构建 |
| 决策3：工作者自由改共享文件 | 生成、宿主与依赖容易交叉覆盖 | 预览可能短暂不一致 | 本地动手快，冲突、失效证据需返工 |

主次判定：决策1优先用户能拿到完整可用条目；决策2优先开发循环成本与真实资料的时效；决策3优先系统输入一致性和成果保护。三者均保持116库的最终覆盖范围。
